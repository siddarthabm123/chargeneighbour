# ChargeNeighbour launch plan
Updated 20 October 2026.

The public site demonstrates the idea and supports pilot recruitment. Commercial charging remains gated.

## Implemented foundation
- Real Google map with optional location snapshot, directions and honest fallbacks.
- On-demand station details and signed photo links, ready for Google API activation.
- Synchronized filtered map markers when a restricted browser key and map ID are configured.
- Supabase email auth, ownership RLS, idempotent applications and paginated account activity.
- Private support receipts without sign-in and restricted operator responses.
- Reviewed host listings, private exact locations and offered schedules.
- Atomic reservation requests, expiring holds and supervised session metering.
- Signed Razorpay captured-payment/full-refund events and a settlement ledger, gated pending provider approval and tests.
- Public pilot privacy/terms, support/data requests, consented campaign measurement, security headers and indexing/share metadata.
- Sanitized error logs, health checks, authenticated daily retention and encrypted small application-data snapshots.

## Owner and provider requirements before advertising
1. Declare the actual legal operator, controlled public contact and first operating area.
2. Activate and test production SMTP with a consenting user outside the Supabase organisation.
3. Finish Google billing/API activation and verify real results, photos and quotas. Never treat a configured key as proof of live availability.
4. Use a hosting plan that permits commercial operation. Establish full provider backups and an approved monitoring/alert destination.
5. Assign operator access to your verified account UUID. Review support requests and host applications.

Recruitment campaigns should offer founding-host applications or pilot interest. They must not promise a confirmed charging slot or guaranteed earnings.

## Requirements before paid charging
1. Verify real hosts, equipment, metering, property permissions, parking/access and support ownership.
2. Establish payment and host-settlement eligibility. Test actual provider order creation, signed webhooks, retries, amount mismatches, refunds and reconciliation in an approved staging setup.
3. Publish entity-specific terms, final pricing/tax treatment, cancellation/refund rules, settlement timing and reachable support coverage.
4. Test independent user accounts and simultaneous reservations with a real database, provider outages, failed access, session interruption and meter disputes.
5. Rehearse full database/Auth/Storage recovery separately from the supplementary application snapshot.
6. Complete supervised sessions before setting the private commercial launch approval flag.

The pilot records externally completed host payouts. Automatic bank transfers and partial refunds remain outside this release. Operator review must resolve ambiguous provider-order failures before any retry.

## Evidence for expansion and pitching
A suggested first validation group is 5–10 verified hosts with 20–30 driver interviews, followed by 30–50 supervised sessions after operational approval. These are planning targets, not traction or industry benchmarks. Select one concentrated area from actual host availability and customer demand while accepting applications nationwide.

Measure successful entry, delivered energy, repeat sessions, failed visits, support/refund cost and contribution after variable costs. Public Google listings, applications and targets are not partner inventory, paying customers or completed sessions. Use the website and pitch brief to demonstrate what is implemented and state outstanding activation requirements clearly.
