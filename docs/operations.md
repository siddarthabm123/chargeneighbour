# ChargeNeighbour operator runbook

The current release is a pilot. Code for reservations, supervised metering and payment reconciliation does not establish merchant approval, legal readiness or verified host supply.

## Activation order

1. **Owner access:** sign in to the website using your own verified account. Visit `/operator` to find its UUID. Assign that UUID through the private `ADMIN_USER_IDS` environment variable, or set trusted Supabase `app_metadata.role` to `operator` using an authorised administration tool. Never use user-editable metadata or email matching to grant access. Redeploy after changing environment configuration.
2. **Identity and support:** provide the actual operating business/person name, a public email you control, and the initial pilot area. Set `BUSINESS_NAME`, `SUPPORT_EMAIL`, and `PILOT_AREA`. The pilot never borrows a different company's identity or contact details. The private support form already works without sign-in once the schema is deployed.
3. **Production email:** configure custom SMTP in Supabase, verify your sending domain, disable click tracking on authentication links, and test a new consenting user outside the organisation. Only then set `EMAIL_SIGNIN_READY=true`. This flag is a status indicator; it does not configure delivery. Test expired links, resend, sign-out and same-browser PKCE return.
4. **Google:** finish billing in the existing ChargeNeighbour Maps project, enable Places API (New), and put the API-restricted server key in `GOOGLE_PLACES_API_KEY`. For synchronized markers, enable Maps JavaScript API and create a separate browser key restricted to the production HTTP referrers, plus a real map ID. Set `GOOGLE_MAPS_BROWSER_KEY` and `GOOGLE_MAPS_ID`. The browser key is intentionally public; the server key must remain private. Confirm photos/attribution and GPS-denied fallback on actual devices. Do not raise quotas before reviewing costs.
5. **Hosting and recovery:** choose a Vercel plan that permits commercial use before business promotion. Configure provider backups for the full Supabase database, Auth and Storage. The operator's encrypted pilot snapshot is a supplementary application-data export capped at 2 MB. Its passphrase stays with the operator. Test restoration in a separate database before relying on any backup.
6. **Host approval:** review the actual applicant's identity, permission, electrical installation, metering, access and support arrangements. In `/operator`, publish only when every check is complete and evidence references exist. Provide genuine host photos with permission. The app rounds public coordinates to neighbourhood precision and keeps the exact address separate. Add offered hours in IST.
7. **Payments:** establish Razorpay merchant and settlement eligibility. Test with an approved staging setup before live credentials. Configure `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` and `RAZORPAY_WEBHOOK_SECRET` privately. Subscribe the merchant webhook to `/api/payments/webhook` for `payment.captured` and `refund.processed`. Verify signing, retries, amount mismatches and reconciliation. The browser's checkout success never marks a session paid.
8. **Commercial policy and acceptance:** publish the actual entity-specific service terms, tax treatment, cancellation/refund rules, settlement timing and support coverage. Verify multi-account access, parallel booking attempts, failed access, meter disputes, payment failures, provider outages and full refunds with consenting pilot participants. Complete supervised sessions and inspect results. Keep `COMMERCIAL_LAUNCH_APPROVED=false` until these gates pass. Turning the flag on is an operator release decision, not proof of compliance or safety.

## Daily operation

- Review support and privacy requests, pending applications, reservation holds and payment reconciliation in `/operator`. Queues load bounded pages and allow older records. A support receipt link grants access to that ticket; do not share it publicly.
- Confirm requested slots within 30 minutes. Requests reserve the interval while held. A charger row lock serializes overlap checking and insertion. Expired holds cease blocking later requests. Confirmed sessions require a separate start action with the actual cumulative meter reading.
- Record completion with the final meter reading and an evidence reference. The database computes energy and the charge from the agreed rate, then records the proposed 15% commission. Treat evidence as sensitive. Do not infer energy from listed maximum power.
- Customers pay after the measured session. Server-created Razorpay orders and signed captured-payment events establish payment. The ledger distinguishes host amounts owed from externally completed settlements.
- For a refund request, review the incident and process any approved **full refund** through the merchant dashboard. The verified refund webhook updates the ledger. Partial refunds and automatic bank transfers are not implemented in this pilot. Do not promise them.
- A network failure while creating a provider order can leave `payment_status=creating`. Do not blindly clear it or create another charge. Inspect the merchant's receipt/session ID, reconcile the actual order, and have an authorised operator repair the mapping after verification. This deliberate pause avoids duplicate orders after ambiguous failures.
- Record an external host payout only after checking the actual transfer and retaining its reference. Reconcile payment fees and tax separately. A ledger row is not evidence of bank settlement.

## Monitoring and retention

- Nearby station discovery and reverse address lookup use the public Photon OpenStreetMap API when Google Places is inactive. The app caps Photon at 200 upstream calls per UTC day and 12 calls per client per ten minutes. Requests are user-initiated, never periodic tracking. The public service has no availability guarantee; before larger campaigns configure an appropriate hosted/private Photon-compatible HTTPS endpoint through `PHOTON_BASE_URL`. Review [Photon's usage guidance](https://github.com/komoot/photon#demo-server). This is a pilot fallback, not a complete charging inventory or a source of live availability. Each GPS refresh makes one station lookup plus one reverse lookup; a city search makes a forward lookup plus one nearby lookup. The clipboard changes only after the user clicks Copy address, and contains readable approximate address text, never coordinates.

- `/api/health` checks application database connectivity and reports configured discovery/email capabilities. It contains no customer records or secrets. Connect an approved uptime monitor and operator alert destination before advertising; no external alert account or recipient is presumed by this repository.
- API failures and Next.js request failures produce sanitized structured logs with operation/reference/time. Inspect Vercel logs and Supabase advisors. Do not add payloads, cookies, email addresses or precise GPS to diagnostic logs.
- A daily Vercel cron calls `/api/maintenance` at 03:15 UTC. Configure a private `CRON_SECRET` so Vercel can authenticate the call. Until it is configured, the endpoint correctly returns 401. `RATE_LIMIT_SECRET` can be separately configured; otherwise daily keyed rate-limit hashes derive from the private server credential.
- Cleanup removes expired quotas after two days, aggregate campaign counts after 13 months, closed/answered support after 90 days without updates, and withdrawn applications after 30 days if no charger depends on them. It preserves open requests and financial records. Withdrawal uses a database timestamp. Review privacy requests individually and verify ownership before disclosure/deletion. Supabase Auth and provider logs require separate handling.
- Optional campaign analytics require consent. The database counts saved applications once even when a submission retries with the same key. Operational queue counts and customer payments must not be presented as advertising-attributed traction without validated evidence.

## Database and publishing

`supabase/migrations/20261019211614_complete_launch_schema.sql` consolidates the legacy baseline, search allowance and launch changes in executable order. `20261019212640_encrypted_pilot_backup.sql` adds the private snapshot function. The files under `docs/migration-history/` are historical source references, not executable migrations.

These migrations were applied through the Supabase SQL editor for this release. Before switching this existing project to CLI-managed pushes, reconcile its migration history with the applied files using the current CLI's documented repair workflow. Do not blindly rerun the full launch migration against an already upgraded database. A new empty database can apply the executable migrations in timestamp order.

Run `npm run check`, `node scripts/check-stations.mjs`, `node scripts/check-safety.mjs`, `node scripts/check-database.mjs`, `npm run build`, and `node scripts/check-http.mjs`. The database test uses isolated PostgreSQL with synthetic fixtures and tests an encrypted application-data restoration. It does not connect to production or certify live SMTP, Google billing, charger safety, merchant approval or multi-connection production concurrency.

Push reviewed source changes to the connected repository's main branch to publish on Vercel. Confirm production `/api/health`, the new pages and protected routes after deployment. Keep server credentials in Vercel Secrets, never Git or downloaded public artifacts.
